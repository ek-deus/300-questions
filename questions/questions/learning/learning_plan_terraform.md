# Terraform

Основные используемые команды:

**terraform init** — инициализирует рабочий каталог Terraform.

**terraform validate** — подтверждает правильность синтаксиса файла Terraform.

**terraform plan** — генерирует файл изменений и показывает, что изменится при запуске. Рекомендуется выполнить эту команду перед запуском команды apply, чтобы убедиться, что результаты будут соответствовать намерениям.

**terraform apply** — строит или изменяет инфраструктуру. Команда покажет план выполнения и потребует ответа «да» или «нет» (если не используется флаг --auto-approve, с которым команда будет выполняться автоматически).

**terraform refresh** — обновляет локальный файл состояния относительно реальных ресурсов. Это гарантирует, что Terraform имеет точное представление о том, что находится в текущей среде.

**terraform destroy** — удаляет инфраструктуру, управляемую Terraform. Это приведет к безвозвратному удалению всего, что создано и сохранено в файле состояния из кластера.

Перед использованием команд переместитесь в рабочую папку с файлами конфигурации **.tf**.

В случаях использования команд в скриптах автоматизации, для удобства, используется опция **-chdir=** для смены рабочей папки перед применением команды:


```tf
terraform -chdir=terraform/configuration apply
```



Terraform — это инструмент, который позволяет описывать инфраструктуру в виде кода и автоматизировать её развёртывание, модификацию и удаление. Он поддерживает множество провайдеров — таких, как AWS, Google Cloud, Azure, Yandex Cloud и других.

Особенности Terraform:


предоставляет декларативный язык для определения инфраструктуры, который позволяет описать желаемое состояние инфраструктуры без необходимости задавать конкретные шаги для ее настройки;
поддерживает широкий диапазон провайдеров, включая AWS, Google Cloud, Microsoft Azure, Yandex Cloud, Selectel и другие, что позволяет использовать один и тот же язык для управления инфраструктурой в различных облачных окружениях;
поддерживает планирование изменений инфраструктуры, что позволяет убедиться в том, что изменения будут безопасными и не приведут к нежелательным результатам;
предоставляет возможность оперировать модулями (логическими абстракциями поверх некоторого набора ресурсов), что упрощает и стандартизирует процесс определения инфраструктуры

Одним из основных преимуществ Terraform является возможность описать желаемое состояние инфраструктуры в виде кода, и затем он автоматически приводит её в это состояние, а вы не заботитесь о ручном управлении каждым ресурсом.

Terraform использует несколько основных элементов для описания инфраструктуры:

*Providers*: провайдеры — это интерфейсы для взаимодействия с ресурсами, такими, как AWS, Google Cloud, Microsoft Azure и т. д.

*Resources*: ресурсы — это объекты, которые вы хотите создать, удалить или изменить. Например, виртуальная машина, балансировщик нагрузки, база данных.

*Variables*: переменные — это значения, которые можно передать в Terraform для конфигурирования вашей инфраструктуры.

*Data Sources*: источники данных — это инструменты, которые позволяют Terraform получать данные из внешних источников, таких как API, базы данных или другие службы.

*Outputs*: выводы — это результаты, которые Terraform выдает после выполнения конфигурации, например, IP‑адреса, идентификаторы ресурсов и т. д.

Дополнительные элементы Terraform, которые стоит упомянуть:

Модули. Позволяют повторно использовать код и упрощают управление сложными инфраструктурами.

Варианты окружения. Terraform позволяет управлять различными версиями инфраструктуры в зависимости от окружения.

Выражения. Terraform использует выражения для вычисления значений и проверки условий.

Итак, мы понимаем, что с помощью Terraform можно описать инфраструктуру в коде, этот код содержится в файлах, что логично🙂, так давайте поговорим с вами о них.

Основные типы файлов, которые вы можете использовать в Terraform, включают в себя:

Файлы конфигурации (`.tf` файлы) — это основные файлы Terraform, которые содержат описание ресурсов, которые вы хотите создать или управлять.

Файлы переменных (`.tfvars` файлы) — это файлы, которые содержат значения переменных, использующихся в файлах конфигурации.

Файл состояния (`.tfstate` файл): это файл, который хранит текущее состояние вашей инфраструктуры. Он обновляется каждый раз, когда вы запускаете apply (конечно, если вы что‑то изменили в коде).

Также, стоит отдельно рассказать про файл состояния ‑`.tfstate`. Terraform сохраняет информацию о текущем состоянии вашей инфраструктуры в файле состояния. Этот файл содержит информацию о ресурсах, которые уже были созданы в вашей инфраструктуре, и их текущих свойствах.

Terraform использует этот файл, чтобы определить, какие ресурсы необходимо изменить, какие создать, а какие необходимо удалить, когда вы запускаете команду apply. Грубо говоря, он помогает Terraform определять, какие изменения необходимо внести в инфраструктуру, чтобы ее состояние соответствовало описанному в конфигурационных файлах.


Terraform 101
Что такое Terraform?

Terraform : «HashiCorp Terraform — это инструмент для управления инфраструктурой как кодом, позволяющий определять как облачные, так и локальные ресурсы в удобочитаемых конфигурационных файлах, которые можно версионировать, повторно использовать и совместно применять. Затем вы можете использовать согласованный рабочий процесс для развертывания и управления всей вашей инфраструктурой на протяжении всего ее жизненного цикла. Terraform может управлять низкоуровневыми компонентами, такими как вычислительные ресурсы, хранилище и сетевые ресурсы, а также высокоуровневыми компонентами, такими как записи DNS и функции SaaS».

В чём заключаются преимущества использования Terraform или инфраструктуры как кода (IaC) в целом?

Полная автоматизация: Раньше создание, изменение и удаление ресурсов осуществлялись вручную или с помощью набора инструментов. С Terraform или другими технологиями IaC вы управляете полным жизненным циклом в автоматическом режиме.
Модульность и возможность повторного использования: написанный вами код для определенных целей можно использовать и комбинировать различными способами. Вы можете написать код для создания ресурсов в общедоступном облаке, и им можно поделиться с другими командами, которые также смогут использовать его в своих учетных записях в том же (или другом) облаке.
Улучшенное тестирование: концепции, подобные CI, легко применимы к проектам и фрагментам кода, основанным на IaC (инфраструктура как код). Это позволяет тестировать и проверять работу программ заранее.
В чём заключается одна из причин, по которой ручные процессы могут быть полезны?

Для изучения платформы на начальном этапе.
Почему при создании масштабируемой инфраструктуры целесообразно избегать использования ручных процессов?
Ручные процессы создания инфраструктуры медленны, поскольку требуют вмешательства человека на каждом этапе, что задерживает развертывание. Они подвержены ошибкам, так как ручная настройка увеличивает риск ошибок и несоответствий. Кроме того, эти процессы трудно воспроизводимы, что затрудняет обеспечение одинаковой конфигурации инфраструктуры в разных средах — в отличие от инфраструктуры как кода (IaC), которая автоматизирует и стандартизирует развертывание.
Какие функции есть у Terraform?

Декларативный подход: Terraform использует декларативный подход (а не процедурный) для определения конечного состояния ресурсов.
Отсутствие агентов: в отличие от других технологий (например, Puppet), где используется модель агента и сервера, в Terraform для выполнения операций используются различные API (облачных сервисов, облачных платформ и т. д.).
Сообщество: Terraform обладает сильным сообществом, которое постоянно публикует модули и исправляет ошибки по мере необходимости. Это обеспечивает качественную поддержку модулей, и пользователи могут довольно быстро получить помощь в любой момент.
Какой язык программирования использует Terraform?

DSL под названием "HCL" (Hashicorp Configuration Language). Декларативный язык для определения инфраструктуры.


Каков типичный рабочий процесс Terraform?

Напишите определения Terraform: .tfфайлы, написанные на языке HCL, описывающие желаемое состояние инфраструктуры (и запускаемые terraform initв самом начале).
Обзор: С помощью такой команды, как [команда], terraform planвы можете получить представление о том, что Terraform будет делать с использованием написанных определений.
Применение определений: Команда terraform applyTerraform применит заданные определения, добавив, изменив или удалив ресурсы.
Это ручной процесс. В большинстве случаев он автоматизирован, поэтому пользователь отправляет запрос на слияние (PR/MR) с предложением изменений в Terraform, существует процесс тестирования этих изменений, и после их слияния они применяются ( terraform apply).


В каких случаях можно использовать Terraform?

Обеспечение и управление инфраструктурой: Вам необходимо автоматизировать или запрограммировать свою инфраструктуру, чтобы вы могли легко тестировать ее, применять и вносить необходимые изменения.
Многооблачная среда: вы управляете инфраструктурой в разных облаках, но ищете единый способ сделать это во всех облаках.
Согласованные среды: Вы управляете такими средами, как тестовая, производственная, промежуточная и т.д., и ищете способ обеспечить их согласованность, чтобы любые изменения в одной из них применялись и в других средах.

В чём разница между Terraform и такими технологиями, как Ansible, Puppet, Chef и т. д.?

Terraform считается технологией IaC (инфраструктура как код). Она используется для выделения ресурсов и управления инфраструктурой на различных платформах.

Ansible, Puppet и Chef — это технологии управления конфигурацией. Они используются, когда запущен экземпляр и необходимо применить к нему какие-либо настройки, например, установить приложение, применить политику безопасности и т. д.

Чтобы было понятно, инструменты управления конфигурацией (CM) можно использовать для выделения ресурсов, поэтому в конечном итоге, для создания инфраструктуры, как Terraform, так и такие инструменты, как Ansible, могут достичь одного и того же результата. Разница заключается в способе работы. Ansible не сохраняет состояние ресурсов, он не знает, сколько экземпляров находится в вашей среде, в отличие от Terraform. В то же время, хотя Terraform может выполнять задачи управления конфигурацией, он имеет меньше модулей поддержки для этой конкретной цели и не отслеживает состояние выполнения задач, как Ansible. Различия существуют, и чаще всего рекомендуется комбинировать технологии: Terraform используется для управления инфраструктурой, а технологии CM — для настройки поверх этой инфраструктуры.

Зависимости
Иногда возникает необходимость ссылаться на некоторые ресурсы в одном или разных файлах .tf. Зачем и как это делается?

Почему: потому что ресурсы иногда связаны или должны быть связаны. Например, вы создаете экземпляр AWS с ресурсом "aws_instance", но в то же время хотите разрешить к нему некоторый трафик (поскольку по умолчанию трафик запрещен). Для этого вы создадите ресурс "aws_security_group", а затем в ресурсе aws_instance укажете на него ссылку.

Имеет ли значение порядок создания ресурсов в Terraform?

Да, когда существует зависимость между различными ресурсами Terraform, вам нужно, чтобы ресурсы создавались в правильном порядке, и именно это и делает Terraform.

Чтобы было еще понятнее, если у вас есть ресурс X, который ссылается на идентификатор ресурса Y, то нет смысла создавать первый ресурс X, потому что у него не будет идентификатора, который можно было бы получить от еще не созданного ресурса.

Поставщики
Объясните, что такое «поставщик услуг».

terraform.io : «Terraform использует плагины, называемые «провайдерами», для взаимодействия с облачными провайдерами, SaaS-провайдерами и другими API... Каждый провайдер добавляет набор типов ресурсов и/или источников данных, которыми Terraform может управлять. Для чего нужны входные переменные в Terraform?

Переменные позволяют определить значение данных в одном месте, вместо того чтобы повторять жестко заданное значение в нескольких разных местах. Таким образом, при необходимости изменения значения переменной, вы делаете это в одном месте, а не меняете каждое из жестко заданных значений.

tuple([<TYPE>, ...])

Объяснение источников данных в Terraform

Источники данных используются для получения данных от поставщиков или, в целом, из внешних ресурсов для Terraform (например, публичных облаков, таких как AWS, GCP, Azure).
Для чтения используются источники данных. Они ничего не изменяют и не создают.
Многие поставщики предоставляют доступ к нескольким источникам данных.

Продемонстрируйте, как использовать источники данных.

data "aws_vpc" "default {
  default = true
}

Как извлечь данные из источника данных?

Общий синтаксис выглядит следующим образом:data.<PROVIDER_AND_TYPE>.<NAME>.<ATTRIBUTE>

Таким образом, если вы определили следующий источник данных

data "aws_vpc" "default {
  default = true
}
Получить атрибут ID можно следующим образом:data.aws_vpc.default.id

Существует ли возможность объединения источников данных? В каких случаях это может быть полезно?

Да, вы можете определить один источник данных, используя другой источник данных, например, в качестве фильтра.

Допустим, мы хотим получить подсети AWS, но только из нашей VPC по умолчанию:

data "aws_subnets" "default" {
  filter {
    name   = "vpc-id"
    values = [data.aws_vpc.default.id]
  }
}

Жизненный цикл
Как происходит обновление ресурса?

По умолчанию текущий ресурс удаляется, создается новый, и все ссылки, указывающие на старый ресурс, обновляются, чтобы указывать на новый ресурс.


Можно ли изменить жизненный цикл по умолчанию? Как? Зачем?

Да, это возможно. Можно выбрать один из нескольких жизненных циклов. Например, "create_before_destroy", который меняет порядок действий: сначала создается новый ресурс, затем обновляются все ссылки со старого ресурса на новый, а потом старый ресурс удаляется.

Как им пользоваться:

lifecycle {
  create_before_destroy = true
}
Зачем это вообще использовать: у вас могут быть ресурсы, имеющие зависимости, которые сами по себе неизменяемы (= вы не можете их изменить, поэтому вам придется создать новый ресурс). В таком случае жизненный цикл по умолчанию не подойдет, потому что вы не сможете удалить ресурс, имеющий зависимость, так как он все еще ссылается на старый ресурс. AWS ASG + конфигурации запуска — хороший пример такого варианта использования.

Объясните, что такое «удалённое состояние». Когда и как его использовать?

Terraform генерирует JSON-файл `terraform.tfstate`, описывающий компоненты/сервисы, развернутые у указанного провайдера. Remote State сохраняет этот файл на удаленном носителе данных для обеспечения совместной работы команды.

Объясните, что такое «блокировка состояния».

Блокировка состояния — это механизм, который блокирует операции над определенным файлом состояния от нескольких вызывающих сторон, чтобы избежать конфликтов между операциями разных членов команды. Как только блокировка операции первого вызывающего стороны будет снята, другой член команды может приступить к выполнению своей операции. Тем не менее, Terraform сначала проверит файл состояния, чтобы убедиться, что необходимый ресурс уже существует, и если нет, то создаст его.

Встроенный способ Terraform — это использование remote-stateдля поиска выходных данных из других модулей. Также в сообществе распространен инструмент, позволяющий terragruntявно внедрять переменные между модулями.

Почему Terraform сохраняет состояние и чем отличаются локальное и удалённое состояние?

Terraform хранит состояние для сопоставления реальных объектов инфраструктуры с ресурсами, объявленными в коде, отслеживания зависимостей, обнаружения отклонений и ускорения планирования за счет кэширования данных атрибутов.


Локальное состояние хранится в terraform.tfstateфайле на диске и подходит для быстрых экспериментов или рабочих процессов с участием одного оператора.
Удаленное состояние хранится в бэкэнде (например, S3, GCS, Terraform Cloud), который может обеспечивать блокировку, контроль доступа и версионирование, чтобы команды использовали единый источник достоверной информации.
Всегда выбирайте удаленный бэкэнд, если конфигурацию обрабатывает более одного оператора или конвейера автоматизации.

Государственный против частного
Репозиторий Git против других местоположений

Файл tfstate содержит учетные данные в открытом текстовом виде. Не следует размещать его в общедоступном месте.
Файл tfstate не следует изменять одновременно, поэтому размещение его в общедоступном месте, имеющем права на запись, может привести к проблемам. (В удаленном состоянии Terraform такой проблемы нет).
Файл tfstate важен. Поэтому лучше хранить его в месте, где регулярно создаются резервные копии и обеспечена надежная защита.

Таким образом, tfstate не следует хранить в репозиториях Git. Лучше использовать защищенные хранилища, такие как защищенные корзины.
Верно или неверно? Редактирование файла состояния Terraform вручную — распространенная практика, и она даже рекомендуется для многих различных сценариев использования.

Неверно. Следует по возможности избегать редактирования файлов состояния Terraform вручную. Предпочитайте поддерживаемые команды, такие как terraform state mv, terraform state rm, или , terraform state replace-providerчтобы CLI обеспечивал согласованность метаданных.

Почему хранение файла состояния локально на компьютере может быть проблематичным?

В целом, хранение файла состояния на вашем компьютере не представляет проблемы. Проблема возникает, когда вы являетесь частью команды, использующей Terraform, и вам необходимо обеспечить его совместное использование. Помимо совместного использования, вам также необходимо обеспечить возможность редактирования файла разными членами команды одновременно, поэтому блокировка также является довольно важным аспектом.

Упомяните некоторые передовые методы, связанные с tfstate.

Не редактируйте его вручную. Параметр tfstate был разработан для управления с помощью Terraform, а не напрямую пользователями.
Храните его в безопасном месте (поскольку он может содержать учетные данные и конфиденциальную информацию в целом).
Регулярно создавайте резервные копии, чтобы при необходимости можно было легко откатить изменения.
Храните данные в удаленном общем хранилище. Это особенно важно при работе в команде, поскольку состояние может быть обновлено любым из членов команды.
Включение версионирования возможно, если хранилище, в котором хранится файл состояния, его поддерживает. Версионирование отлично подходит для резервного копирования и отката в случае возникновения проблем.
Назначьте «владельцев состояния», которые будут проверять доступ, менять учетные данные и выполнять миграцию.
Не допускайте попадания .tfstateфайлов и .terraform/каталога в систему контроля версий ( .gitignore) и шифруйте любые резервные копии, созданные без предварительного создания.
Как и почему следует избегать одновременного редактирования файла состояния?

Если два пользователя или процесса одновременно редактируют файл состояния, это может привести к созданию некорректного файла состояния, который фактически не отражает состояние ресурсов.

Чтобы этого избежать, Terraform может применять блокировку состояния, если бэкенд это поддерживает. Например, AWS S3 поддерживает блокировку состояния и обеспечение согласованности через DynamoDB. Часто, если бэкенд это поддерживает, Terraform автоматически использует блокировку состояния, поэтому от пользователя ничего не требуется для её активации. Конвейеры автоматизации должны ждать снятия блокировок, а не принудительно разблокировать их.

Terraform Backend
Что такое бэкенд Terraform? Какой бэкенд используется по умолчанию?

Бэкенд Terraform определяет, как хранится и загружается состояние Terraform. По умолчанию состояние локальное, но можно установить удаленный бэкенд.

Как настроить бэкенд AWS S3 с блокировкой состояния DynamoDB?

Используйте удалённый бэкэнд, когда вам нужен общий, надёжный источник достоверной информации. Минимальная конфигурация выглядит следующим образом:

terraform {
  required_version = ">= 1.6.0"

  backend "s3" {
    bucket         = "my-tfstate-bucket"
    key            = "prod/network/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "tf-locks"
    encrypt        = true
  }
}
Перед включением бэкэнда создайте S3-хранилище с версионированием, шифрованием по умолчанию и блокировкой публичного доступа.
Создайте таблицу в DynamoDB с первичным ключом LockID, чтобы Terraform мог получать блокировки.
Используйте политики минимальных привилегий IAM, разрешающие только операции с состоянием корзины и таблицы, чтобы уменьшить масштаб последствий.
Какие команды помогают проверять, переносить и безопасно управлять состоянием Terraform?

terraform init -migrate-state
terraform plan -refresh-only
terraform state list
terraform show -json | jq '.values.root_module.resources[].address' | head
terraform state mv module.vpc.aws_subnet.public[0] module.vpc.aws_subnet.public_a
terraform init -migrate-state: перемещает существующий локальный файл состояния в настроенный бэкэнд с блокировкой.
terraform plan -refresh-only: обнаруживает изменения путем обновления атрибутов удаленного объекта без предложения изменений.
terraform state list: подтверждает, какие объекты отслеживаются в состоянии после миграции или импорта.
terraform show -json: включает в себя скриптовые проверки (в данном случае в паре с jq), позволяющие проверять адреса или метаданные.
terraform state mv: переименовывает или перемещает ресурсы/модули без их повторного создания, что полезно во время рефакторинга.
Какие передовые методы обеспечивают безопасность и надежность состояния Terraform?

Зашифруйте и версионируйте свой удалённый бэкэнд (например, aws_s3_bucket_versioningс использованием SSE-KMS на S3).
Внедрите блокировку (в DynamoDB, GCS или Terraform Cloud Workspaces) и отслеживайте зависшие блокировки.
Предоставьте IAM минимальные привилегии и чередуйте ключи доступа; автоматизация должна принимать на себя роли с кратковременными учетными данными.
Запланируйте автоматическое резервное копирование бэкэнда (репликация S3, PITR DynamoDB) и периодически проверяйте восстановление данных.
Документируйте ответственность "владельца состояния", порядок реагирования на инцидент и шаги по устранению неполадок при разблокировке или ручном редактировании (это должно быть крайней мерой).
Как осуществить миграцию с локального сервера на новый удалённый бэкэнд?

Выделение ресурсов бэкэнда (например, хранилища S3 с версионированием и таблицы DynamoDB) осуществляется из отдельной конфигурации начальной загрузки.
Добавьте блок бэкенда в конфигурацию Terraform и запустите команду terraform init -migrate-state.
Проверьте миграцию с помощью terraform state listили terraform state pullи сохраните надежную резервную копию предыдущего файла.
Удалять или архивировать локальные файлы terraform.tfstateследует только после подтверждения корректной работы новых планов с удаленным бэкэндом.
Чем terraform applyотличается рабочий процесс при использовании удалённого бэкэнда?

Начинается все с получения блокировки состояния, чтобы другие не могли одновременно изменять состояние. Кроме того, приложение загрузит последний снимок состояния перед планированием и атомарно загрузит обновленное состояние после завершения выполнения.

Как будет происходить процесс переключения с удалённого бэкэнда на локальный?

Вы удаляете код бэкэнда и выполняете действия terraform init, чтобы вернуться к localбэкэнду.
Вы удаляете ресурсы, которые представляют собой сам удалённый бэкэнд.
Заархивируйте последний удаленный файл состояния, чтобы иметь возможность восстановить данные в случае повреждения локальной копии.
Верно или неверно? Использовать переменную в конфигурации бэкэнда НЕВОЗМОЖНО.

Это правда, и это довольно существенное ограничение, поскольку это означает, что вам придется обращаться к ресурсам удаленного бэкенда и копировать некоторые значения в конфигурацию бэкенда.

Один из способов решения этой проблемы — использовать частичные конфигурации в совершенно отдельном файле от самого бэкенда, а затем загружать их с помощью terraform init -backend-config=some_backend_partial_conf.hcl.


Существует ли способ получить информацию из удалённого бэкенда/состояния с помощью Terraform?

Да, используя концепцию источников данных. Существует источник данных для удаленного состояния, называемый "terraform_remote_state".

Вы можете использовать его со следующим синтаксисом.data.terraform_remote_state.<NAME>.outputs.<ATTRIBUTE>


Как удалённый бэкенд состояния улучшает взаимодействие в проекте Terraform?

Хранение файла состояния в общем месте позволяет нескольким людям или процессам работать с одним и тем же состоянием. Удалённый бэкенд состояния улучшает совместную работу над проектами Terraform, решая основную проблему обмена состоянием инфраструктуры. Когда команда работает над инфраструктурой, каждому необходим доступ к текущему состоянию для безопасного внесения изменений, а блокировка предотвращает конфликты.

Истинный


Почему рабочие пространства могут быть не лучшим решением для управления состояниями различных сред, таких как тестовая и производственная?

Одна из причин заключается в том, что все рабочие пространства хранятся в одном месте (то есть в одном бэкэнде), и обычно нежелательно использовать один и тот же контроль доступа и аутентификацию как для тестовой, так и для производственной среды по очевидным причинам. Кроме того, работа в рабочих пространствах довольно подвержена человеческим ошибкам, поскольку вы можете случайно подумать, что находитесь в одном рабочем пространстве, в то время как работаете в совершенно другом.

Существуют ли какие-либо ограничения для метааргумента "подсчета"?

countне поддерживается внутри строчного блока
Возможности работы со списками довольно ограничены. Вы заметите, что изменение элементов в списках или даже такие операции, как удаление, иногда интерпретируются неожиданным образом. Например, удаление элемента из списка может переместить другие элементы на новую позицию, а поскольку каждая позиция представляет собой ресурс с счетчиком, это может привести к тому, что будут изменены и удалены некорректные ресурсы. Существуют способы решения этой проблемы, но использование счетчика со списками все же не всегда просто.
Что такое цикл for_each? Чем он отличается от цикла "count"?

Функция for_each может применяться только к коллекциям, таким как карты или множества (в отличие от функции count, которая может применяться к спискам).
Функция for_each помогает справиться с ограничением, countкоторое не является оптимальным для случаев использования при изменении списков.
Функция for_each поддерживает встроенные блоки, в отличие отcount
Продемонстрируйте, как использовать цикл for_each.

resource “google_compute_instance” “instances” {

  for_each = var.names_map
  name = each.value
}

Аргументы, влияющие на жизненный цикл ресурса (его создание, изменение и т. д.) и поддерживаемые Terraform независимо от типа ресурса, в котором они используются.

count: сколько ресурсов создать на основе одного определения ресурса.
Жизненный цикл: как обрабатывать создание или удаление ресурсов.

count: сколько ресурсов создать на основе одного определения ресурса.
Жизненный цикл: как обрабатывать создание или удаление ресурсов.
depends_on: создает зависимость между ресурсами

Кроме того, модули отлично подходят для создания многократно используемого кода Terraform, который можно совместно использовать не только в разных репозиториях, но и в рамках одного репозитория, в разных средах (например, на промежуточном и производственном серверах). Хорошо спроектированные модули также предоставляют небольшую, четко определенную структуру и скрывают детали реализации.


Что представляет собой модуль кода Terraform? Иными словами, что такое модуль с практической точки зрения?

По сути, любой файл или файлы в каталоге являются модулем в Terraform. Для определения модуля не требуется специальный синтаксис. Корневая конфигурация сама по себе является модулем, и любой модуль, вызываемый из неё, считается дочерним модулем.

Необходимо версионировать и продвигать изменения инфраструктуры с помощью семантических релизов и конвейеров непрерывной интеграции.

path.root: путь к корневому модулю

Вы управляете ASG с помощью Terraform, а это значит, что у вас также есть ресурсы "aws_launch_configuration". Проблема в том, что конфигурации запуска неизменяемы, и иногда их нужно менять. Это создает проблему, когда Terraform не может удалить ASG, потому что они ссылаются на старые конфигурации запуска. Как с этим справиться?

Добавьте следующее в ресурс "aws_launch_configuration".

lifecycle {
  create_before_destroy = true
}
Это изменит порядок работы Terraform. Сначала он создаст новый ресурс (конфигурацию запуска), затем обновит другие ресурсы, чтобы они ссылались на новую конфигурацию запуска, и, наконец, удалит старые ресурсы.
